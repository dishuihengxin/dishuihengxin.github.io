事务里读不到自己刚看到的数据？聊聊 InnoDB 的 MVCC

博主
2026-03-01
2 分钟
244 字
--

去年有个业务同学在群里 @ 我，说他们的页面刷新时数据时有时无，怀疑数据库出了问题。远程看了半天，代码里是这样的：开一个事务，先查一次配置表，中间做了几百毫秒的业务处理，再查一次同一张表。第一次查到的是刚改过的值，第二次又变回旧的了。他问我，是不是数据库抽风。

数据库没抽风，抽风的是我们对隔离级别的理解。这篇文章把这事背后的机制完整讲一遍，因为后来我发现，把 MVCC 真正搞懂的人，比自以为懂的多不了几个。

版本链：一行数据的多个前世

InnoDB 存一行数据时多带两个隐藏列：DB_TRX_ID（最后修改这行的事务号，单调递增，指向 undo log 里旧版本的指针和 DB_ROLL_PTR）。每次更新，旧版本被抄进回滚段，新行指回它，串成链：

( trx_id=102, val='C' )   ← 表里的当前行
   ↑ roll_ptr
( trx_id=98,  val='B' )   ── undo log
   ↑ roll_ptr
( trx_id=90,  val='A' )   ── undo log

注意 update 走的是"抄旧写新"，行不搬地方；而 DELETE 是先打删除标记（也带 trx_id，作为活跃号的上界，事务提交后由 purge 线程真正回收。这个细节后面讲长事务时会用到。

ReadView：拍快照与四条判断规则

ReadView 是查询开始时拍下的快照，核心字段四个：创建者自己的 trx_id、生成时刻仍活跃的事务号集合 m_ids、其中最小的 min_trx_id、以及即将分配的下一个事务号 next_trx_id）。拿它去比对版本链上每行的 DB_TRX_ID，规则四条：

  1. trx_id < min_trx_id：修改者早已提交，可见；
  2. trx_id == 自己的：本事务改的，可见；
  3. min_trx_id <= trx_id < next_trx_id 且在 m_ids 里：未提交，不可见，顺链走旧一格重判；
  4. trx_id >= next_trx_id：快照之后才开启的事务，不可见。

拿一组真实号推一遍就再也不会忘。假设 100 已提交、101 和 102 活跃，我是 101，此刻查询：

ReadView: m_ids={101,102}, min=101, next=103

trx=100 → 100<101          → 可见 ✓
trx=102 → 在 m_ids          → 不可见，走旧版本
trx=98  → 可见 ✓（走两步之后）

RC 与 RR 的全部区别就一句话：RC 每条快照读新建一个 ReadView，RR 只在事务第一条快照读时建一个。用双会话实验看最直观：

-- 会话 A（RR）                        -- 会话 B
BEGIN;
SELECT val FROM t WHERE id=1;   -- 'B'
                                     UPDATE t SET val='C' WHERE id=1;
                                     COMMIT;
SELECT val FROM t WHERE id=1;   -- 还是 'B'！
SELECT val FROM t WHERE id=1;   -- 还是 'B'（RR 不会换照片）
COMMIT;
SELECT val FROM t WHERE id=1;   -- 现在 'C'

开头那个工单的谜底就在这个实验里：业务代码的事务恰好相当于会话 A。

两个最常被误读的点

MVCC 只管快照读。 UPDATE、DELETE、SELECT ... FOR UPDATE、FOR SHARE、还有唯一键冲突检查，全走当前读：读最新版本并加锁。所以 RR 下会出现"普通 SELECT 看不见新行，UPDATE 却把账记到它头上"的现象，这不是 bug，是两套读各司其职。依赖"重复读"做业务判断的临界区，要么显式 FOR UPDATE，要么干脆把隔离级别降到 RC 省心。顺带一提，RR 下普通 select 不加锁、看不到的行也不会因为 update 而出现幻读报错，但 INSERT ... SELECT 这类语句在 RR 下会加间隙锁防止源表幻影，历史上坑过不少人。

undo 不是无限深的。 purge 线程只回收"对所有活跃 ReadView 都不可见"的旧版本。看积压的老命令是 SHOW ENGINE INNODB STATUS，输出里找这一行：

------------
TRANSACTIONS
------------
History list length 274    ← 越大说明旧版本积压越多，健康态应该是个位数到几百

想看更细的，8.0 里用 SELECT * FROM information_schema.INNODB_TRX ORDER BY trx_started;，重点盯 trx_started 和 trx_rows_modified 两个字段。

长事务：MVCC 的天敌

把 purge 的规则想通，长事务的危害就是自然推论：一个跑了几小时的事务拿着最老的 ReadView，之后所有已提交的旧版本它都"可能要看"，purge 一个都不敢动。Undo 膨胀、版本链越走越长、CPU 无故升高，全是这一个原因。我处理过最夸张的一次，History list length 涨到四百多万，一个批量任务在事务里循环调外部接口，每个接口三秒超时。

所以后来团队立了规矩：事务里不准调 RPC、不准传文件，事务只包数据库操作；监控上事务超过 60 秒告警。参数层面的配套是 innodb_undo_tablespaces（独立 undo 表空间，避免与系统表空间一起膨胀）和 8.0 的 innodb_rollback_segments 调大，但说实话，参数只是缓冲，纪律才是根治。

回到那位同学。我让他把循环查询挪到事务外，问题当场消失。他把案例写进 Wiki，标题叫《MySQL 不是你想象的那个样子》。这标题起得比我这篇文章好。
